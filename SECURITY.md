# Security remediation and release evidence

This work changes product behavior: trials come from Apple/Google store offers, new recordings require a fresh signed RevenueCat response, and the database is encrypted with a device-bound key. Existing notes remain readable without a subscription. There is no local three-day eligibility counter.

## Findings and disposition

Numbers refer to the original 38-finding audit. **Implemented** means source changes are present, not that a release binary or physical device has been certified.

| Findings | Disposition and relevant code |
| --- | --- |
| 1–2 local trial resets / clock manipulation | Implemented: removed local trial authorization. Store trials require actual store eligibility and a verified entitlement. Reinstalling cannot issue a new local trial. Store offer configuration remains required. `src/lib/entitlement.ts`, `src/lib/storePlans.ts`. |
| 3 future-dated purchase cache | Implemented: reject negative, nonfinite and expired cache ages. New recording authorization requires a server-signed response newer than both the SDK baseline and the securely persisted last authorization. |
| 4 foreground subscription expiry | Implemented: check entitlement expiration using an advancing monotonic clock, refresh on foreground/update, and stop recording when access expires. A timer cannot prevent suspension by the OS; returning to foreground rechecks. |
| 5 modified client | **Architectural limit:** a device owner controlling the executable can patch an offline inference feature. Signatures prevent network forgery, not arbitrary process modification. Enforcing payment against this threat requires a paid server operation with server-side authorization. This repository contains no such backend; attestation alone would not make offline execution unpatchable. |
| 6–10 lock, key authentication, settings, default, weak biometrics | Removed: app lock was dropped at the owner's request. The database opens at startup after screen protection initializes and never asks for biometrics. A legacy biometric-protected key is never read; its database is kept aside (see 14). |
| 11 native dialogs | Mitigated: replace destructive native delete confirmation with an in-app confirmation; check the note and active state at deletion; database work runs through one queue. OS dialogs and menus still need the device matrix below. |
| 12 screen privacy | Implemented: await native protection before mounting the notes tree; show failure/retry; use distinct native request tags on retry and share pending initialization. Privacy wording acknowledges platform limitations. Device verification remains required. |
| 13 keyboard / clipboard | Mitigated: disable transcript selection, editor context menus, autocorrection, spell checking and autofill; bound all editor inputs. A third-party keyboard still receives typed characters. Users must choose a trusted keyboard; an app cannot revoke keyboard or OS access to input. |
| 14 missing / damaged database key | Implemented: a damaged key preserves the database and surfaces a recoverable error. A missing key renames the database and its sidecars to `spokflow-unreadable-<time>.db` unchanged, then starts a new database; notes are never deleted or overwritten. Lost keys cannot be reconstructed. |
| 15 plaintext migration | Implemented: fail visibly on migration or cleanup errors; verify encrypted checkpoint success before clearing legacy rows; enable secure deletion, truncate legacy WAL, vacuum and delete sidecars; preserve conflicting records instead of overwriting/deleting them. Flash wear leveling and old OS backups prevent guarantees of physical erasure. |
| 16 iOS backup exclusion | Implemented in native plugin: throwing directory setup, complete file protection, backup exclusion with readback before React Native starts; stop startup if protection cannot be applied. Regeneration preserves code added by other plugins and moves older protection blocks ahead of React initialization. Needs an iOS build/device test. |
| 17 memory retention | Mitigated: unmount notes on lock, clear transcript references, wipe owned PCM after native use and on cancellation, clear committed text collections. JavaScript strings and native/model/OS copies cannot be reliably erased by JavaScript; do not claim protection against a fully compromised process. |
| 18 unbounded recording | Implemented: 15-minute capture limit, 90-second pending-audio limit, PCM alignment validation, transcript limit, and controlled stop on processing/storage errors. Limits apply before accepting additional PCM. |
| 19 oversized notes / list memory | Implemented: paginate 40 summaries, read only short previews in the list, reject oversized editor records, and enforce title/transcript/item limits at persistence and import boundaries. Invalid or oversized legacy checklists are preserved and rejected by the editor instead of silently dropping items before a later write. |
| 20–22 failed edits, lost concurrent updates, query errors | Implemented: serialize database work; apply checklist changes to the current persisted row; update UI only after writes succeed; retain failed edit drafts and show retry/loading failures. |
| 23 recording loss | Mitigated: persist completed transcription batches as encrypted checkpoint notes before finalization and reuse their IDs on final save. Saved batches survive process death. Audio not yet decoded is deliberately not written to disk and can still be lost on force termination or suspension. |
| 24 recovery | Implemented for supported notes: explicit password-encrypted SQLCipher export/import, bounded streaming import in a transaction, passphrase confirmation, and temporary encrypted-file cleanup. Export validates restore compatibility before sharing. Limits are 10,000 notes and 100 MB; oversized or damaged legacy records are preserved but require separate recovery. Automatic OS backups remain disabled. Only a previously exported backup can recover a lost device/key; no forgotten-password reset exists. Native round-trip/wrong-password tests remain required. |
| 25–26 signing / native config drift | Source plugins reject missing release credentials and apply backup/transfer/SQLCipher configuration. Generated projects must be regenerated and the produced artifact verified; source configuration alone is insufficient evidence. Local test signing is forbidden on EAS. |
| 27 artifact verification | Implemented: independent expected certificate fingerprint; manifest permissions/export allowlist, cleartext/debug/backup restrictions, complete transfer rules, model hash, bundled bytecode and native-library checks. Both EAS Android profiles require a Gradle verification task before archive upload, including companion release APK and production AAB checks. Library presence is not proof of runtime SQLCipher; iOS and device evidence are still required. |
| 28 model substitution | Implemented: hash the existing Android destination; recopy and verify if corrupt, including same-size corruption. Verify again in the built artifact. |
| 29 unsupported dependencies | Upgraded to Expo SDK 57 / React Native 0.86 / TypeScript 6 and replaced expo-av with expo-audio. Upgrade compatibility must pass dependency, bundle and native checks before release. **Remaining development-tool maintenance risk:** Expo's React lint plugin still requires ESLint 9; see the upstream limitation below. |
| 30–33 dependency advisories | Patched PostCSS, decode-uri-component and uuid versions are pinned through overrides. image-size is no longer present in the upgraded lockfile. A guarded postinstall adapter preserves query-string's CommonJS API with the patched ESM decoder; its real query parser has a compatibility regression check. Latest audit and build results are recorded below. |
| 34 native patches | **Unverified on devices:** JavaScript checks exercise lifecycle/buffer policy; they do not establish absence of C++/JNI races or memory corruption. Run the native stress/sanitizer matrix below for both patched packages. |
| 35 ineligible iOS trial advertising | Implemented: query eligibility; show introductory terms only for an explicitly eligible response. Unknown/ineligible responses show regular pricing. |
| 36 incomplete subscription terms | Implemented: render each Android pricing phase and its cycle count, show eligible iOS intro terms, use the displayed Android subscription option for purchase, and hide unsupported/ambiguous offers. |
| 37 refund notification setup | **External configuration required:** RevenueCat/App Store/Play dashboards are not available in this workspace. Verify server notifications and actual refund/revocation propagation before distributing. |
| 38 anonymous restore policy | **External configuration required:** use `Transfer to new App User ID` for this anonymous-only app, then test purchases/restores across reinstall and devices. The dashboard steps and primary references are below; the actual project setting has not been inspected or changed. |

## Release checks

The installed Expo lint configuration uses [eslint-plugin-react 7.37.5, whose declared peers exclude ESLint 10](https://github.com/jsx-eslint/eslint-plugin-react/blob/master/package.json). Its compatible ESLint 9 line is [end-of-life](https://eslint.org/version-support/). This development-tool maintenance gap remains; an advisory-free dependency report does not establish ongoing maintenance.

Run `npm ci`, `npm run typecheck`, `npm run lint`, `npm run check`, `npm run check:signing` (JDK required), `npx expo install --check`, `npx expo-doctor`, and `npm audit`. The regression checks mock native boundaries and do not prove encryption or native-thread correctness.

For Android regenerate with `npx expo prebuild --platform android --no-install`, then use `npm run apk`. Provide the existing upload keystore through `SPOKFLOW_UPLOAD_STORE_FILE`, `SPOKFLOW_UPLOAD_STORE_PASSWORD`, `SPOKFLOW_UPLOAD_KEY_ALIAS`, `SPOKFLOW_UPLOAD_KEY_PASSWORD`. Do not create an unrelated key for an already published app. Set `SPOKFLOW_SIGNING_SHA256` to an independently verified SHA-256 fingerprint of that release/upload certificate. The APK verifier must not derive its expectation from the artifact it checks. On EAS, managed signing credentials are injected by EAS; set the expected upload fingerprint separately. Play-delivered APKs use the Play App Signing certificate, so verify those against that separately obtained fingerprint.

`SPOKFLOW_TEST_BUILD=1` only allows a local test artifact. It is not release evidence and must never be distributed. Production EAS builds produce both APK and AAB from the same release variant, verify the APK manifest, and separately verify the AAB certificate and assets. Both Android profiles invoke `:app:verifySpokflowRelease`; its dependency tasks build the artifacts and a failing verification fails Gradle before EAS uploads them. The earlier success-hook placement was too late: [Expo's build sequence](https://docs.expo.dev/build-reference/android-builds/) uploads the application archive before that hook. The Android verifier does not cover iOS; inspect its signed archive independently.

Configure both public RevenueCat SDK keys and the legal publisher details in `app.json`. No secret RevenueCat API key belongs in the client. In RevenueCat, all advertised products must grant `pro`; configure store trials and store server notifications, verify receipt/entitlement verification support, and test anonymous restore transfer behavior. Use sandbox purchases, cancellations, refunds, reinstalls, a second device, and returning ineligible subscribers. Never substitute a successful purchase for evidence that refund and restore behavior works.

The AAB signature verifier uses the independently pinned public certificate as its sole trust anchor for `jarsigner -verify -strict`, with an explicit certificate validity check. Ordinary verification can return success with unsigned entries; [the JDK documentation](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jarsigner.html) defines the strict failure for this case. No release private key is needed for verification. Disposable test keys are used only by the signature regression fixtures and are removed afterward.

## RevenueCat dashboard work still required

These are the concrete settings for the current anonymous-only app, checked against RevenueCat's documentation on September 26, 2026. They have **not** been applied: the workspace has no authenticated store or RevenueCat dashboard connection.

1. Under RevenueCat Project settings > General, select **Transfer to new App User ID**. Use the same behavior for sandbox validation. RevenueCat specifies this option for apps without login; purchases owned by anonymous IDs can be aliased during restore. The setting covers every app in the project, so review any other apps sharing it. [Restore behavior](https://www.revenuecat.com/docs/projects/restore-behavior).
2. For iOS, copy the notification URL supplied by the RevenueCat app settings into both App Store Connect notification environments, using Version 2. RevenueCat also offers a button to apply both URLs. If the app already forwards notifications elsewhere, preserve that integration through RevenueCat forwarding. [Apple notification setup](https://www.revenuecat.com/docs/platform-resources/server-notifications/apple-server-notifications).
3. For Android, connect RevenueCat's Google Play app settings to the correct Cloud Pub/Sub project, then put its generated topic into Play Console's monetization notification settings. Include subscriptions, voided purchases and every one-time product. Send a test event and verify that RevenueCat records a recent receipt time. If tracking purchases directly from notifications is enabled, select anonymous IDs for identity detection because this app uses the SDK. [Google notification setup](https://www.revenuecat.com/docs/platform-resources/server-notifications/google-server-notifications).
4. Test an actual sandbox subscription and lifetime purchase, restore on another installation, and verify refund/revocation propagation to `pro`. Apple non-subscription refund detection depends on server notifications. For Google subscriptions, a refund without revocation does not remove access; store-originated refunds can take up to 24 hours to reach RevenueCat. A fresh signed client response cannot discover an event RevenueCat has not received. Record the dashboard event and the app's denied recording attempt, while confirming existing notes still open after authentication. [Refund behavior](https://www.revenuecat.com/docs/subscription-guidance/refunds).
